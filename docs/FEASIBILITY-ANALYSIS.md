# 可行性分析 — 交付形态与平台选择

> 版本：v1.0
> 日期：2026-05-15
> 背景：核心交互从传统表单转向 AI 对话式，需要重新评估交付平台

---

## 一、核心问题

产品定位升级为"教练成长助手"后，核心交互变成：
1. **自然语言/语音录课**（"明天3点张三普拉提"）
2. **课后语音速记**（"小林深蹲进步很大，右膝代偿注意"）
3. **AI 课前建议主动推送**（开课前自动交付参考卡）
4. **体态评估结构化录入**（拍照+语音描述→结构化报告）

这些交互对平台的要求是：**语音输入 + AI 处理 + 主动推送 + 拍照存储**。

问题：当前的微信小程序能不能撑住这个交互模式？

---

## 二、微信小程序能力边界

### 能做的 ✅

| 能力 | 说明 |
|------|------|
| 语音录入 | `wx.getRecorderManager()` 支持前台录音，可录 10 分钟 |
| 拍照/相册 | `wx.chooseMedia()` 拍照选图，完全支持 |
| 网络请求 | HTTPS 请求，支持调用自有服务端 API |
| 本地存储 | 10MB localStorage，够存文本数据 |
| 分享 | 小程序卡片分享，截图分享 |
| 扫码打开 | 线下场景快速进入 |
| 内嵌 WebView | 可嵌 H5 页面，扩展能力 |

### 有限制的 ⚠️

| 能力 | 限制 | 影响 |
|------|------|------|
| 推送消息 | 订阅消息需用户主动订阅，每次一条，模板需审核 | AI 建议"主动推送"受限，只能"打开 App 后展示" |
| 后台运行 | 小程序进入后台 5 秒后挂起 | 不能后台录音、后台处理 |
| 长连接 | WebSocket 可用但后台断开 | 实时推送依赖前台 |
| 语音转文字 | 微信自带 `wx.getRealtimeSpeechRecognizer()`，但识别质量一般 | 复杂专业术语（筋膜松解、三腔对位）可能识别不准 |
| AI 对话审核 | 涉及 AI 生成内容需走内容安全审核 | 纯对话式交互可能被审核打回 |
| 存储上限 | 10MB 本地，照片不能存本地 | 体态照片必须上传到服务端/云存储 |

### 做不到的 ❌

| 能力 | 说明 |
|------|------|
| 主动 Push 通知 | 不能像 App 一样"课前 30 分钟推送提醒" |
| 后台语音唤醒 | 不能"嘿 Siri"式唤醒录课 |
| 本地大模型 | 无法在端侧运行 AI |
| 持久化后台任务 | 不能在后台持续运行 agent |
| 自定义通知样式 | 订阅消息模板固定，无法富文本 |

## 三、交付形态对比

### 方案 A：微信小程序 + 服务端 AI（当前路线增强）

```
教练在小程序前台操作
    → 语音/文字发送到服务端
    → 服务端 AI 处理（parse/建议/结构化）
    → 结果返回小程序展示
```

**优点：**
- 零安装，微信生态内触达
- 教练群体高度依赖微信，获客成本低
- 已有代码基础，迭代快
- 小程序码贴在瑜伽馆就能引流

**缺点：**
- 推送能力弱（"打开才能看"，不能"主动告诉你"）
- AI 交互深度受审核限制
- 照片存储需要云服务（成本）
- 体验天花板受微信平台约束

**可行性：80%** — 核心功能都能做，但"主动推送"和"深度对话"受限

---

### 方案 B：微信公众号 + 小程序（对话入口分离）

```
公众号（对话入口）：
    教练发消息"明天3点张三普拉提" → AI 解析 → 回复确认卡片
    课前自动推送建议卡片（48小时内可推）

小程序（展示+管理入口）：
    课表查看、会员管理、体态评估、照片管理
```

**优点：**
- 公众号天然支持对话交互，无审核压力（已有客服消息能力）
- 48 小时消息窗口内可主动推送
- 小程序处理复杂 UI（课表、评估表单、照片）
- 两者互相跳转，体验连贯

**缺点：**
- 48 小时窗口限制（用户最后一次消息后 48 小时内才能推）
- 需要教练关注公众号（多一步）
- 公众号消息格式有限（不如小程序 UI 丰富）
- 维护两个载体，开发成本增加

**可行性：70%** — 对话体验好，但 48h 窗口和双载体增加复杂度

---

### 方案 C：H5 PWA（渐进式 Web App）

```
教练添加到手机主屏
    → 类 App 体验，全屏运行
    → Web Push 通知（Android 完整支持，iOS 16.4+ 支持）
    → 语音录入用 Web Speech API
    → 无平台审核限制
```

**优点：**
- 无微信审核约束，AI 交互自由度最高
- 支持 Push 通知（课前提醒、建议推送）
- 一套代码跨平台
- 当前 H5 代码可直接升级为 PWA

**缺点：**
- iOS Safari 上 Web Push 体验一般（需要 PWA 已安装到主屏）
- 需要教练主动"添加到主屏幕"（不如小程序扫码方便）
- 语音识别依赖浏览器实现，质量参差
- 离开微信生态，失去社交传播优势

**可行性：60%** — 技术最自由，但获客和教练习惯是硬伤

---

### 方案 D：原生 App（iOS + Android）

**优点：**
- 完整推送、后台、语音、相机能力
- 体验天花板最高
- 可做本地 AI 加速

**缺点：**
- 开发成本最高（两个平台）
- 安装摩擦大（教练要去 App Store 下载）
- 审核周期长
- 种子期用户量不支撑原生投入

**可行性：30%** — 现阶段不合理，用户量上来后可以考虑

---

### 方案 E：Agent 形态（纯对话式，如 MCP/CLI/Bot）

```
教练在某个对话界面和 AI 交互
    → "排课：明天3点张三普拉提"
    → "记录：小林今天深蹲进步大"
    → "查看：下周课表"
    → AI 全部处理，返回结构化结果
```

**优点：**
- 交互最简——一切通过自然语言
- 开发只需关注 API + AI，无 UI 负担
- 未来可接入任何前端（微信、App、网页、语音助手）

**缺点：**
- **课表可视化**无法通过纯对话完成（"好看的课表"需要 UI）
- **体态照片管理**纯对话体验差
- **用户认知门槛高**——教练不一定理解"和 AI 对话"的心智模型
- 缺乏"实体感"——教练需要一个"打开就能看的东西"

**可行性：作为底层 40%，作为唯一形态 20%**

## 四、推荐方案：A+E 混合架构

```
┌─────────────────────────────────────────┐
│            交互层（多端可选）              │
│  ┌──────────┐  ┌──────────┐  ┌────────┐ │
│  │ 微信小程序 │  │  H5/PWA  │  │ 未来App │ │
│  └────┬─────┘  └────┬─────┘  └───┬────┘ │
│       │              │             │      │
│  ┌────▼──────────────▼─────────────▼────┐ │
│  │        AI Agent 层（服务端）          │ │
│  │  ┌─────────────────────────────────┐ │ │
│  │  │  自然语言解析 │ 课前建议生成     │ │ │
│  │  │  语音转文字   │ 体态报告结构化   │ │ │
│  │  │  批量排课解析 │ 课后记录整理     │ │ │
│  │  └─────────────────────────────────┘ │ │
│  │                                      │ │
│  │  ┌─────────────────────────────────┐ │ │
│  │  │        业务 API 层              │ │ │
│  │  │  排课 CRUD │ 会员管理 │ 评估管理 │ │ │
│  │  │  照片存储   │ 配置管理 │ 统计    │ │ │
│  │  └─────────────────────────────────┘ │ │
│  └──────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

### 核心思路

**底层是 Agent（API + AI），上层是 UI 壳。**

- 服务端设计为 **AI Agent + 业务 API** 的组合
- 微信小程序和 H5 都是"瘦客户端"，只负责展示和输入采集
- AI 能力全部在服务端，前端只需要：发送输入 → 展示结果
- 未来如果要切换平台（PWA、原生 App、甚至接入微信公众号对话），只需要换壳

### 阶段执行

| 阶段 | 交付物 | 重点 |
|------|--------|------|
| **当前** | 微信小程序 + H5 | 打磨课表 UI、基础 CRUD、种子用户验证 |
| **Phase 1** | + 服务端 AI Agent | 自然语言录课、课后速记、基本建议 |
| **Phase 2** | + 体态评估模块 | 照片存储、结构化评估、报告生成 |
| **Phase 3** | 评估平台切换 | 根据用户反馈决定是否加 PWA 通知/公众号对话 |

### 关于微信审核风险

最大的不确定性：**微信是否允许小程序内的 AI 对话式交互**。

缓解策略：
1. 不做开放式聊天框，做"结构化 AI 辅助"（语音→解析结果→确认）
2. AI 生成内容走微信内容安全 API 过滤
3. 前端呈现为"智能表单"而非"聊天窗口"——本质是 AI 但形态不是聊天
4. 如果审核被拒，AI 交互降级到 H5 WebView 内嵌

## 五、关于"会不会做成了一个 Agent"的回答

**会，而且应该这样做。但不是"只做 Agent"。**

正确的思路：
- 底层确实是一个 Agent（接收自然语言 → 理解意图 → 调用业务 API → 返回结构化结果）
- 但上层**必须有可视化 UI**——课表要好看、照片要能看、评估报告要能分享
- 教练的心智模型不是"和 AI 对话"，而是"打开一个 App 看我的课表"
- AI 应该是**无感的基础设施**，不是**产品形态本身**

类比：
- Notion 底层有 AI，但你打开看到的是页面和数据库，不是聊天框
- Apple Calendar 可以用 Siri 录入，但你看到的是漂亮的日历视图
- 我们要做的：**录入靠 AI（自然语言/语音），展示靠 UI（课表/评估报告/会员档案）**

---

## 六、结论

| 决策点 | 结论 |
|--------|------|
| 当前平台 | **保持微信小程序 + H5 双端**，验证核心价值 |
| 服务端 | **按 Agent 架构设计**，AI 能力 + 业务 API 分层 |
| AI 交互形态 | **"智能表单"而非"聊天窗口"**——语音/文字输入 → 结构化预览 → 一键确认 |
| 推送能力 | 小程序订阅消息做基础提醒，不强求"主动推送" |
| 平台迁移 | Phase 3 根据数据决定，架构上预留多端扩展能力 |
| 短期不做 | 原生 App、公众号对话入口、纯 Agent/CLI 形态 |
